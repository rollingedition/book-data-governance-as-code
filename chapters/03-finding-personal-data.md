# Finding personal data

By the end of this chapter you can find personal data on a data platform automatically. You'll propose a classification for every column from its name, its type and a reproducible sample of its values, find personal data inside free text span by span, and measure each detector against labelled data, so you know what it misses before anyone relies on it. You'll run Presidio's pattern recognizers offline with thresholds chosen by measurement, compare them with the recorded detections of a model trained to find personal data, and classify again only the columns a schema change adds.

The platform, the online learning platform this book follows, sells professional courses to adult learners, and keeps its warehouse in an Iceberg catalog of eight source tables, each under the namespace of the team that runs it. [Chapter 2](#a-catalog-you-can-test) gave every column a classification in `governance/metadata.toml`, a file people review. A reviewed file records what its reviewers believe a column holds, and on the platform three beliefs need checking. `billing.payments.card_number` is a legacy column whose description says it holds full card numbers, and nobody has checked. `crm.learners.notes` is free text that support agents type, so its name says nothing about what's in it. And learners write whatever they like in support tickets and course reviews, so a classification of the whole column can't protect that text: the platform has to find each name, email and phone number inside it before the text can be masked span by span, which [chapter 9](#replace-personal-data) does to reviews before the platform's course assistant learns from them.

This chapter builds the book's shared module for this, `lib.pii`: rules on column names, seeded samples of a column's values, a Presidio detector configured to run offline, and code that scores any detector against labelled data. Every detector in this chapter is measured against one file, which we call the truth: `data/platform/pii_spans.parquet`. The script that generated the platform's data writes it beside the tickets and reviews: every piece of personal data it placed in their text, with its exact start and end. Invoice numbers, order numbers and the date a problem happened stay unlabelled, because the platform doesn't treat them as personal data.

The platform's phone numbers, card numbers and IBANs are random in a valid format, so any one may be in service, and no example prints one whole: it masks all but the last four digits.

## Classify columns from the schema {#classify-columns-from-the-schema}

The cheapest evidence about a column is its schema: its name and its type. A rule on names reads no data, so it can run over a whole catalog in a pull request, and it catches the columns whose names say what they hold, such as `email` or `date_of_birth`. Catalog tools start the same way: OpenMetadata's auto-classification begins with a "Column Name Scanner", which validates "the column names of the table against a set of regex rules" ([OpenMetadata docs](https://docs.open-metadata.org/v2.0.x/how-to-guides/data-governance/classification/auto-classification/auto-pii-tagging)). The type decides what comes next. A text column's values can be sampled and scanned. A timestamp can't hold an email, and scanning one with a date pattern would flag every row, so numbers, dates, timestamps and booleans are classified by name alone.

The platform keeps its rules in `governance/pii.toml`, the file that holds every setting of its detector and is reviewed like the metadata. The rules are {{out:column-name-rules:name rules}} regular expressions on lowercased column names, each naming the entity it suggests, and the first match wins. The same file maps each entity to a classification: a phone number to `personal`, a card number or an IBAN to `sensitive`. `lib.pii.by_name` applies the rules. Run them over every column of the catalog, and compare them with the reviewed metadata:

[Example: column-name-rules](../examples/column-name-rules.py)

Of the catalog's {{out:column-name-rules:columns in the catalog}} columns, the rules mark {{out:column-name-rules:columns a name rule marks}}, and all {{out:column-name-rules:of them, agreeing with the metadata}} agree with the classification people gave them. The rules miss three columns the reviewers classified `personal`: `crm.learners.notes`, `learning.reviews.body` and `support.tickets.body`. All three are free text, where a name describes the container, not its contents. And the one marked column the platform worries about most, `billing.payments.card_number`, gets `sensitive` from its name without anyone learning what it holds: whole card numbers, the last four digits, or a payment provider's token would all match `card_?(number|num|no)`.

Name rules are brittle in a known way. The authors of Sherlock, a model for detecting column types, observed that "these matching-based approaches often are not robust to dirty data and only detect a limited number of types" ([Hulsebos et al., 2019](https://arxiv.org/abs/1905.10688)). So the platform reads values too, in the {{out:column-name-rules:columns of text, whose values can be sampled}} text columns its catalog holds.

**Working rule:** Run name rules over every column first, because they're free, and let them raise a classification, never lower one. Keep the rules short, in code, and reviewed like any other rule. Treat any free-text column, whatever it's called, as one that needs its values sampled, and classify columns of other types by name alone.

## Run Presidio offline {#run-presidio-offline}

To read values, the platform uses Presidio, an open-source library for finding and masking personal data. Its analyzer runs a set of **recognizers**: regular expressions with checksums, phone-number parsing, and a named-entity model reached through an NLP engine. The engine has two jobs, as Presidio's docs put it: "NER based PII identification, and feature extraction for downstream rule based logic (such as leveraging context words for improved detection)", and its default model is spaCy's `en_core_web_lg` ([Presidio docs](https://github.com/data-privacy-stack/presidio/blob/2.2.364/docs/analyzer/customizing_nlp_models.md)). At {{version:presidio-analyzer}}, `AnalyzerEngine()` with no arguments downloads that model when it isn't installed ([source](https://github.com/data-privacy-stack/presidio/blob/2.2.364/presidio-analyzer/presidio_analyzer/nlp_engine/spacy_nlp_engine.py)), so a pipeline without network access fails on its first line, and one with access installs a model of about 400 MB as a side effect ([en_core_web_lg 3.8.0](https://github.com/explosion/spacy-models/releases/tag/en_core_web_lg-3.8.0)).

`lib.pii.detector` configures the engine explicitly instead, with `NoOpNlpEngine`, which "loads no external model" ([source](https://github.com/data-privacy-stack/presidio/blob/2.2.364/presidio-analyzer/presidio_analyzer/nlp_engine/no_op_nlp_engine.py)). The cost is context words. Presidio raises a pattern's score when a word such as "phone" appears near the match, by comparing "each recognizer's context terms with the lemma of each token in the sentence" ([Presidio docs](https://github.com/data-privacy-stack/presidio/blob/2.2.364/docs/tutorial/06_context.md)), and with no model there are no lemmas, so the engine "cannot use context words from the analyzed text". One more call reaches the network: the email recognizer checks domains with tldextract ([source](https://github.com/data-privacy-stack/presidio/blob/2.2.364/presidio-analyzer/presidio_analyzer/predefined_recognizers/generic/email_recognizer.py)), which "fetches the latest Public Suffix List on first use" ([tldextract {{version:tldextract}} README](https://github.com/john-kurkowski/tldextract/blob/5.4.0/README.md)). An empty `TLDEXTRACT_PUBLIC_SUFFIX_LIST_URLS` turns that off if it's set "before importing `tldextract`", as the README says, and importing Presidio imports tldextract. So `lib/__init__.py`, which Python runs before any module of the book's `lib`, sets it. When an example imported Presidio first, the same file replaces tldextract's shared extractor ([source](https://github.com/john-kurkowski/tldextract/blob/5.4.0/tldextract/tldextract.py)) with one that has no URLs. `lib.pii` refuses to load if any remain, and tldextract uses the copy it ships with, so the same text gives the same answer on every machine.

Load every predefined recognizer on that engine, and run it on one of the platform's support tickets:

[Example: presidio-offline-engine](../examples/presidio-offline-engine.py)

Asked whether `en_core_web_lg` is installed, spaCy answers {{out:presidio-offline-engine:en_core_web_lg installed}}, so a bare `AnalyzerEngine()` would try to download it, and tldextract has {{out:presidio-offline-engine:URLs tldextract would fetch the Public Suffix List from}} URLs to fetch its list from. The no-model engine loads {{out:presidio-offline-engine:recognizers loaded}} recognizers instead, and none of them looks for names: the colleague in the ticket, Jennifer Abbott, goes unnoticed. Her email is found with a score of {{out:presidio-offline-engine:EMAIL_ADDRESS on jennifer.abbott@example.net}}, and its domain is found again as a URL, at {{out:presidio-offline-engine:URL on example.net}}. The learner's phone number, an 11-digit number typed without separators, is found three times: as a phone number at {{out:presidio-offline-engine:PHONE_NUMBER on •••••••0440}}, a US bank number at {{out:presidio-offline-engine:US_BANK_NUMBER on •••••••0440}} and a US driver's licence at {{out:presidio-offline-engine:US_DRIVER_LICENSE on •••••••0440}}. Even the phone number is found by chance: the learner's country is {{out:presidio-offline-engine:the learner's country}}, and of Presidio's default regions, the US among them, the digits are valid only in {{out:presidio-offline-engine:default regions where it's valid}}, Brazil. The date of the problem, `12/03`, which says nothing about anyone, is a date at {{out:presidio-offline-engine:DATE_TIME on 12/03}}.

Those scores aren't probabilities. Each pattern carries a constant score, low for weak patterns, as Presidio's tutorial explains: "Zip regex patterns (essentially 5 digits) are very weak, so we would want the initial confidence to be low" ([Presidio docs](https://github.com/data-privacy-stack/presidio/blob/2.2.364/docs/tutorial/06_context.md)). A US bank number is any run of 8 to 17 digits ([supported entities](https://github.com/data-privacy-stack/presidio/blob/2.2.364/docs/supported_entities.md)), and the FAQ admits that "A driver's license number, for example, could be any 9-digit number" ([FAQ](https://github.com/data-privacy-stack/presidio/blob/2.2.364/docs/faq.md)). And the analyzer's default threshold is {{out:presidio-offline-engine:default score threshold}}, so every weak match comes back.

**Working rule:** Configure Presidio's engine explicitly: `NoOpNlpEngine` when you run patterns only, or a pinned model you install yourself when you need its names. Never call `AnalyzerEngine()` bare in a pipeline, and pin anything a recognizer would download, such as the Public Suffix List. Read each score as a constant set for its pattern, never as a probability.

## Sample a column's values the same way every run {#sample-column-values}

Scanning every value of every text column is too slow for a warehouse of any size, so tools sample: OpenMetadata's workflow "samples rows directly from the source and validates them against an Entity Recognition engine" ([OpenMetadata docs](https://docs.open-metadata.org/v2.0.x/how-to-guides/data-governance/classification/auto-classification/auto-pii-tagging)). A sample needs three decisions. **Which rows:** a random sample, not the first rows or a block from a random start. Google's Sensitive Data Protection, for one, offers `RANDOM_START`, where "Scanning starts from a randomly selected row" ([Google Cloud docs](https://cloud.google.com/sensitive-data-protection/docs/inspecting-storage)) and reads on from there, and on a table ordered by sign-up date, that's one cohort. **The same rows every run**, so a classification can be reproduced and a change in it means the data changed. And **how many**, from how rare the data you must catch is.

DuckDB's reservoir sample takes a seed, but its docs warn that "fixing the seed only guarantees a reproducible sample when DuckDB runs single-threaded (`SET threads = 1`)" ([DuckDB {{version:duckdb}} docs](https://duckdb.org/docs/2.0/sql/samples)). `lib.pii.sample` sets one thread, filters out NULLs and then draws a seeded reservoir sample. Draw 20 notes from `crm.learners` twice, then work out how many you'd need:

[Example: seeded-column-sample](../examples/seeded-column-sample.py)

Asked whether a second draw returns the same 20 notes, the example answers {{out:seeded-column-sample:second draw, same notes as the first}}, and the third note already holds a phone number, which the output masks. Of {{out:seeded-column-sample:learners}} learners, {{out:seeded-column-sample:learners with notes}} have notes, and {{out:seeded-column-sample:notes holding personal data the detector finds}} of those hold personal data that the platform's detector, [tuned later in this chapter](#tune-the-recognizers), finds. If p is the share of values holding personal data, the chance that n sampled values include at least one is

chance = 1 − (1 − p)ⁿ

and the n that gives a 99% chance is ln(0.01) / ln(1 − p). This is a rule of thumb: it treats the draws as independent, which a sample without replacement from thousands of rows nearly is. Counted over all rows, NULLs included, personal data is rare, and 20 sampled rows catch it only {{out:seeded-column-sample:chance 20 sampled rows catch one}} of the time; a 99% chance takes {{out:seeded-column-sample:sampled rows needed for a 99% chance}} rows. Counted over the notes that exist, 20 catch it {{out:seeded-column-sample:chance 20 sampled notes catch one}} of the time, and {{out:seeded-column-sample:sampled notes needed for a 99% chance}} are enough for 99%. The NULLs were diluting the sample.

**Working rule:** Sample non-null values, with a fixed seed, on one thread, and keep the seed with the result. Size the sample from the rarest personal data you must catch, with n = ln(0.01) / ln(1 − p) for 99%. The platform samples {{out:seeded-column-sample:values the platform samples per text column}} values per text column, set in `governance/pii.toml`, which catches personal data held by {{out:seeded-column-sample:rarest share that sample catches 99% of the time}} values or more 99% of the time. For anything rarer, scan the whole column, or classify it by rule.

## Classify columns from their values {#classify-columns-from-their-values}

[The name rules](#classify-columns-from-the-schema) and [a reproducible sample](#sample-column-values) combine into one proposal per column. `lib.pii.classify` takes the strictest classification that either supports: the entity the name suggests, and every entity found in at least one sampled value. A column with no evidence gets `internal`, because a detector that found nothing has shown nothing, and only a person decides that a column is `public`. Strictest is a choice. Presidio's own tool for tables, Presidio structured, gives each column one entity, and its default is "Most Common", which "Identifies the most frequently occurring PII entity in a data column or field" ([Presidio docs](https://github.com/data-privacy-stack/presidio/blob/2.2.364/docs/structured/index.md)). That suits choosing how to mask a column. For classifying it, a column that holds one card number in 200 values still holds card numbers.

A proposal stricter than the reviewed metadata is a finding for the table's owner, who raises the classification or records why not; never let a detector lower one. OpenMetadata skips a column "already tagged as `PII`"; we recommend sampling every text column on every run instead, because the reviewed tag is the thing being checked.

## Measure a detector against labelled spans {#measure-against-labelled-spans}

A column-level answer is enough to classify `support.tickets.body`, but not to mask it: masking replaces each span of personal data in each text, and a span the detector misses stays readable. To know what a detector misses, compare its spans with [the truth](#finding-personal-data), the labelled spans of every ticket and review. Two matching rules are standard, and `lib.pii` applies both. **Exact** matching, from the CoNLL-2003 shared task, counts an entity "correct only if it is an exact match of the corresponding entity in the data file" ([Tjong Kim Sang and De Meulder, 2003](https://aclanthology.org/W03-0419.pdf)): the detector found the span with the same boundaries and a label of its type. **Overlap** matching asks only for one shared character, still with a label of its type, which the SemEval-2013 task on drug interactions calls "Type matching" ([Segura-Bedmar et al., 2013](https://aclanthology.org/S13-2056.pdf)). Neither credits a span hidden under another label, so `lib.pii` adds a third measure, **coverage**: whether every character of the span is inside some detection, whatever its label. Each answers a different question. Exact asks whether the detector labelled the whole span right, overlap whether it noticed the span as what it is, and coverage whether masking its detections hides the span.

`lib.pii.score` computes exact and overlap matching as **recall**, the share of labelled spans of each type that a detector finds with a label of that type, and **precision**, the share of each label's detections that match a labelled span. `lib.pii.coverage` gives the share of each type's spans that are covered. `score` also counts the texts in which every labelled character falls inside some detection, the texts masking would leave with nothing personal. The Text Anonymization Benchmark counts a person as protected only "if all of its mentions are masked" ([Pilán et al., 2022](https://aclanthology.org/2022.cl-4.19.pdf)); the platform counts whole texts, which is stricter. And recall comes first: Presidio's evaluation guide says "recall is often more important than precision, as we'd like to avoid missing any PII" ([Presidio docs](https://github.com/data-privacy-stack/presidio/blob/2.2.364/docs/evaluation/index.md)).

Weigh recall first. Before you trust a detector on your text, label a few hundred real records by hand and measure on those too.

## Tune the recognizers against the truth {#tune-the-recognizers}

[Presidio's defaults](#measure-against-labelled-spans) return every weak match, and the FAQ names the remedies: "1. Change the acceptance threshold", and "2. Remove unnecessary PII recognizers, if the dataset does not contain these entities", noting that "there is a trade-off between false positives (falsely detected text) and false negatives" ([FAQ](https://github.com/data-privacy-stack/presidio/blob/2.2.364/docs/faq.md)). Presidio {{version:presidio-analyzer}} adds "per-recognizer and per-entity score threshold configuration", with the analyzer's default threshold "as the fallback" ([changelog](https://github.com/data-privacy-stack/presidio/blob/2.2.364/CHANGELOG.md), [release notes](https://github.com/data-privacy-stack/presidio/releases/tag/2.2.364)). The phone recognizer has one more setting that matters on a platform whose learners live in many countries: the regions whose numbering plans it reads ([source](https://github.com/data-privacy-stack/presidio/blob/2.2.364/presidio-analyzer/presidio_analyzer/predefined_recognizers/generic/phone_recognizer.py)).

`governance/pii.toml` keeps {{out:tune-pattern-recognizers:recognizers kept}} recognizers, for the identifiers the platform's text can hold, each with its own threshold. | Texts fully masked | {{out:tune-pattern-recognizers:Presidio's defaults, texts with every labelled span masked}} | {{out:tune-pattern-recognizers:one threshold of 0.5, texts with every labelled span masked}} | {{out:tune-pattern-recognizers:kept recognizers, own thresholds, texts with every labelled span masked}} | {{out:tune-pattern-recognizers:kept recognizers, learners' phone regions, texts with every labelled span masked}} |

The obvious fix fails. One threshold of 0.5 removes the weak matches and every phone number with them, because a phone number scores {{out:presidio-offline-engine:PHONE_NUMBER on •••••••0440}} when no context word can raise it. Keeping {{out:tune-pattern-recognizers:recognizers kept}} recognizers, with the phone recognizer's threshold at its own score, raises precision to {{out:tune-pattern-recognizers:kept recognizers, own thresholds, precision, exact}} and keeps phone recall where it was. Presidio's default regions are {{out:tune-pattern-recognizers:phone regions, Presidio's default}}; the learners live in {{out:tune-pattern-recognizers:phone regions, the learners' countries}}, and reading their numbering plans raises phone recall to {{out:tune-pattern-recognizers:kept recognizers, learners' phone regions, phone recall, exact}}.

One number goes the wrong way: fewer texts come out fully masked than with the defaults. The recognizers the platform dropped had been masking some phone and card numbers under the wrong label, and a wrong label still hides the digits: without them, coverage falls from {{out:tune-pattern-recognizers:Presidio's defaults, phones covered, any label}} to {{out:tune-pattern-recognizers:kept recognizers, own thresholds, phones covered, any label}} for phone numbers and from {{out:tune-pattern-recognizers:Presidio's defaults, cards covered, any label}} to {{out:tune-pattern-recognizers:kept recognizers, own thresholds, cards covered, any label}} for card numbers. We think precision of {{out:tune-pattern-recognizers:kept recognizers, own thresholds, precision, exact}} is worth that price, because detections are the evidence a reviewer reads, and with the defaults the tickets and reviews hold {{out:measure-pattern-recognizers:US_BANK_NUMBER, detections}} bank numbers and {{out:measure-pattern-recognizers:US_DRIVER_LICENSE, detections}} driver's licences, none of them real. `governance/pii.toml` maps neither entity to a classification, so they change no proposal, but each is a finding someone has to read and dismiss. Dropping the US recognizers is also a claim about the platform's text: the truth holds no US bank or licence numbers. If the platform ever asks for one, that claim, and the measurement, must change.

**Working rule:** Never run with Presidio's default threshold of 0, or with one threshold for every recognizer. Keep only the recognizers for identifiers your text can hold, set each one's threshold from its own scores, and read phone numbers in the regions your users live in, derived from your data. Put all of it in code, and measure again whenever it changes.

## See where patterns fail {#where-patterns-fail}

[The tuned recognizers](#tune-the-recognizers) score well on totals, and totals hide where they fail. The platform's tickets plant cases of each kind, as its data card says: names typed in lowercase, initials, first names that are ordinary words, phone numbers typed without separators, and invoice numbers, order numbers and dates of a problem, which [the truth](#finding-personal-data) leaves unlabelled. ## Compare a PII model {#compare-a-named-entity-model}

[The patterns](#where-patterns-fail) have nothing for names or addresses, and those are most of the personal data in the platform's text: {{out:measure-pattern-recognizers:PERSON, labelled}} names and {{out:measure-pattern-recognizers:LOCATION, labelled}} addresses among the {{out:measure-pattern-recognizers:labelled spans}} labelled spans. Finding them takes a model that reads context, and a general named-entity model is the wrong one. The authors of the SPY dataset "define PII entities as those that can be used to identify, contact, or locate a specific individual", and found that "dedicated NER models exhibit limitations when applied to PII-specific contexts" ([Savkin et al., 2025](https://aclanthology.org/2025.naacl-srw.23.pdf)). We use a PII model, one trained for personally identifiable information: OpenAI's Privacy Filter, an Apache-2.0 model with eight fixed labels, such as `private_person`, `private_address` and `account_number` ([model card](https://huggingface.co/openai/privacy-filter/blob/7ffa9a043d54d1be65afb281eddf0ffbe629385b/README.md)). The labels are the model's: it "does not support configuring label policies dynamically at runtime" ([OpenAI, 2026](https://cdn.openai.com/pdf/c66281ed-b638-456a-8ce1-97e9f5264a90/OpenAI-Privacy-Filter-Model-Card.pdf), section 4.2). We chose it over the runner-up among open PII models, GLiNER2-PII, for those fixed labels: GLiNER2-PII "conditions on the labels you provide at inference time" and takes a threshold ([model card](https://huggingface.co/fastino/gliner2-privacy-filter-PII-multi/blob/1cb4166094dc58fa8d836429f060d6c95f62b495/README.md)), so its recording would have to pin both. Privacy Filter has 1.5 billion parameters, 50 million of them active, and runs on a CPU.

The book's examples never run a model, so they read a recording of its output. The recording, `data/recorded/pii-entities/`, which this chapter and [chapter 9](#replace-personal-data) use, holds every span the model found in every ticket and review, with its offsets, its text and the model's label. `recordings/pii_entities.py` made it on a CPU with the model's reference decoder, `opf` ([code](https://github.com/openai/privacy-filter/tree/f7f00ca7fb869683eb732c010299d901457f19c3)), which chooses the best sequence of labels for a whole text, so most spans come back in one piece rather than token by token. It used the default operating point, all six of the decoder's transition biases at 0 ([calibration file](https://huggingface.co/openai/privacy-filter/blob/7ffa9a043d54d1be65afb281eddf0ffbe629385b/original/viterbi_calibration.json)), which can be set "for improved recall" instead (section 2.3.2). The manifest pins the model's revision and the SHA-256 of its weights, so anyone can record it again and compare, and `lib.pii.recorded` refuses spans that don't match the text at their offsets. The recording keeps the model's labels. The example maps them to the truth's entity types, `account_number` to both card numbers and IBANs, so a different mapping never needs a new recording. Score the model, the platform's patterns, and both together, masking whatever either finds:

Classification does, because `governance/pii.toml` maps each entity type to a classification, a phone number to `personal` and a card number to `sensitive`. ## Classify again when the schema changes {#reclassify-on-schema-change}

A classification describes a column at one moment, and [chapter 2](#catch-schema-changes) showed how schemas move under it. The question is when to run the classifier again. Not on every schema ID: in PyIceberg, editing a column's description gives the schema a new ID with no new column. What needs classifying is a [field ID](#key-column-metadata-by-field-id), the number Iceberg gives each column, that the metadata has never seen, because Iceberg gives every added column a new one, and a renamed column keeps its ID and so its reviewed classification. Values can also change while the schema stays the same, so the samples of text columns need a rerun on a schedule as well. Vendors promise this as a service: Databricks says its classification's "scanning is incremental and optimized to ensure all new data is classified without manual configuration" ([Databricks docs](https://docs.databricks.com/aws/en/data-governance/unity-catalog/data-classification)), a claim we don't test.

On the platform, the support team wants a number to call learners back on for tickets opened by phone, and adds a column called `callback_number` to `support.tickets`. Edit a description first, then add the column, fill it from the learners' phone numbers, and classify only the field IDs that `governance/metadata.toml` lacks:

[Example: reclassify-new-columns](../examples/reclassify-new-columns.py)

## What goes wrong in production {#personal-data-in-production}

A detector fails quietly. Its output always looks like a list of findings, and what it misses never appears in it:

- **Phone numbers read as bank numbers.** With Presidio's defaults, every run of 8 to 17 digits is a US bank number, and every phone number typed without separators is one. The evidence for the ticket table lists hundreds of bank numbers that aren't there, a report of "bank numbers in tickets" sends someone to the wrong team, and mapping that entity to a classification would raise columns for the wrong reason. Keep only the recognizers your text needs, with thresholds of their own, as [the tuning section](#tune-the-recognizers) does, and notice the problem by counting detections per label: a label with hundreds of hits and no labelled spans is a false positive.
- **Names in free text missed.** Patterns find no names, and [the model](#read-the-models-misses) misses some lowercase names, first names that are also words, and first names standing alone. Ticket {{out:privacy-filter-hard-cases:first ticket with a lowercase name both detectors miss}} still says "this is {{out:privacy-filter-hard-cases:the name, as typed}}, i still can't log in" after both detectors have run, and passes every check that counts detections. You notice only by measuring recall against labelled text, per hard case, and by reading a sample of masked output.
- **Personal data in a column called `notes`.** No name rule marks it, and a reviewer who never read it classifies it `internal`. Sample every text column's values, and treat free-text columns as personal until a sample says otherwise.
- **A column more sensitive than its metadata.** Learners paste card numbers into tickets, so `support.tickets.body` holds `sensitive` data under a `personal` classification. Compare every proposal with the reviewed metadata, and route a stricter one to the table's owner.
- **A detector that reaches the network.** `AnalyzerEngine()` downloads a model, and tldextract fetches the Public Suffix List. Offline, the pipeline fails; online, the same text can be classified differently on two machines. A setting read at import holds only if it's made before anything imports the library. Configure the engine, pin what it would fetch, check that the setting held, and run the detector's tests with the network off.
- **Truth shaped by its generator.** The platform's text comes from {{out:measure-pattern-recognizers:sentence templates the texts are built from}} sentence templates filled by Faker, which writes every date of birth one way, phone numbers that aren't valid where the learner lives, and street names built from people's names. Read the misses before trusting a recall figure, and measure again on labelled samples of your own text.

## What this chapter decided {#personal-data-decisions}

- **Columns are classified from their name, their type and their values.** Name rules run on every column; text columns are sampled; the strictest evidence wins, with `internal` as the floor, and only a person sets `public`.
- **Samples are reproducible:** {{out:seeded-column-sample:values the platform samples per text column}} non-null values per text column, by a seeded reservoir sample on one DuckDB thread.
- **Presidio runs offline,** on `NoOpNlpEngine`, with {{out:tune-pattern-recognizers:recognizers kept}} recognizers, each with its own threshold, phone regions read from the learners' countries, and tldextract's own copy of the Public Suffix List, checked when `lib.pii` loads.
- **Detectors are measured against labelled spans,** by exact and overlap matching with a label of the right type and by coverage whatever the label, as recall per entity type, precision per label and texts left with nothing personal, with recall weighed first.
- **A proposal stricter than the metadata is a finding:** `support.tickets.body` goes to `team-support` as `sensitive`, and `billing.payments.card_number` to `team-billing`, with the evidence that it holds full card numbers.
- **Free text is masked with two detectors:** OpenAI's Privacy Filter, recorded at a pinned revision and operating point, for names and addresses, and the tuned patterns for card numbers, IBANs and phone numbers, whose checksums keep card numbers labelled as cards. Masking hides whatever either finds; neither is trusted to make text anonymous.
- **No example prints a whole phone number, card number or IBAN:** `lib.pii.masked` keeps the last four digits.
- **Reclassification follows field IDs:** every field the metadata lacks is classified in the pull request that adds it, and text columns are sampled again on a schedule.
