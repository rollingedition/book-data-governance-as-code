# Finding personal data

By the end of this chapter you can find personal data on a data platform automatically, and say how much of it you miss. You'll propose a classification for every column from its name, its type and a reproducible sample of its values; find personal data inside free text, span by span; and measure each detector against labelled data before anyone relies on it. Along the way you'll run Presidio's pattern recognizers offline, with thresholds chosen by measurement, compare them with the recorded detections of a model trained to find personal data, and classify again only the columns a schema change adds.

Every column on the platform already has a classification. [Chapter 2](#a-catalog-you-can-test) put one in `governance/metadata.toml`, a file people review, and a reviewed file records what its reviewers believe a column holds. On the platform, the online learning platform whose warehouse this book governs, three of those beliefs have never been checked. `billing.payments.card_number` is a legacy column whose description says it holds full card numbers, and nobody has looked. `crm.learners.notes` is free text that support agents type, so its name says nothing about what's in it. Learners write whatever they like in support tickets and course reviews. No classification of a whole column can protect that text. Before it can be masked, the platform has to find each name, email and phone number in it, span by span, as [chapter 9](#replace-personal-data) does for reviews before the course assistant learns from them.

This chapter builds the book's shared module for the job, `lib.pii`: rules on column names, seeded samples of a column's values, a Presidio detector configured to run offline, and code that scores any detector against labelled data. Every detector in this chapter is measured against one file, which we call the truth: `data/platform/pii_spans.parquet`. The platform's data generator writes it beside the tickets and reviews, with every piece of personal data it placed in their text and its exact start and end. Invoice numbers, order numbers and the date a problem happened stay unlabelled, because the platform doesn't treat them as personal data.

Phone numbers, card numbers and IBANs in this book are random, as [the data card](#governance-end-to-end) says, and no example prints one whole: it masks all but the last four digits.

## Classify columns from the schema {#classify-columns-from-the-schema}

The cheapest evidence about a column is its schema: its name and its type. A rule on names reads no data, so it runs over a whole catalog in a pull request, and it catches the columns whose names say what they hold, such as `email` or `date_of_birth`. Catalog tools start the same way: OpenMetadata's auto-classification begins with a column name scanner that checks names against regular expressions ([OpenMetadata docs](https://docs.open-metadata.org/v2.0.x/how-to-guides/data-governance/classification/auto-classification/auto-pii-tagging)). The type decides what comes next. A text column's values can be sampled and scanned, but a timestamp can't hold an email, and scanning one with a date pattern would flag every row. So numbers, dates, timestamps and booleans are classified by name alone.

The platform keeps its rules in `governance/pii.toml`, which holds every setting of its detector and is reviewed like the metadata. The rules are {{out:column-name-rules:name rules}} regular expressions on lowercased column names, each naming the entity it suggests, and the first match wins. The same file maps each entity to a classification: a phone number to `personal`, a card number or an IBAN to `sensitive`. `lib.pii.by_name` applies the rules. The rules go over every column of the catalog, and the results sit beside the reviewed metadata:

[Example: column-name-rules](../examples/column-name-rules.py)

The rules agree with the metadata wherever they fire, and they miss the free text. Of the catalog's {{out:column-name-rules:columns in the catalog}} columns, the rules mark {{out:column-name-rules:columns a name rule marks}}, and all {{out:column-name-rules:of them, agreeing with the metadata}} agree with the classification people gave them. They miss three columns the reviewers classified `personal`: `crm.learners.notes`, `learning.reviews.body` and `support.tickets.body`. All three are free text, where a name describes the container, not its contents. The marked column the platform worries about most, `billing.payments.card_number`, gets `sensitive` from its name without anyone learning what it holds. Whole card numbers, the last four digits, or a payment provider's token would all match `card_?(number|num|no)`.

Name rules are brittle in a known way. The authors of Sherlock, a model for detecting column types, report that name matching isn't robust to dirty data and detects only a few types ([Hulsebos et al., 2019](https://arxiv.org/abs/1905.10688)). So the platform reads values too, in the {{out:column-name-rules:columns of text, whose values can be sampled}} text columns its catalog holds.

**Working rule:** Run name rules over every column first, because they're free, and let them raise a classification, never lower one. Keep the rules short, in code, and reviewed like any other rule. Treat any free-text column, whatever it's called, as one that needs its values sampled, and classify columns of other types by name alone.

## Run Presidio offline {#run-presidio-offline}

To read values, the platform uses Presidio, an open-source library for finding and masking personal data. Its analyzer runs **recognizers**: regular expressions with checksums, phone-number parsing, and a named-entity model reached through an NLP engine. That engine does two jobs, named-entity recognition and feature extraction for rules, such as the context words that raise a score. Its default model is spaCy's `en_core_web_lg` ([Presidio docs](https://github.com/data-privacy-stack/presidio/blob/2.2.366/docs/analyzer/customizing_nlp_models.md)). At {{version:presidio-analyzer}}, `AnalyzerEngine()` with no arguments downloads that model when it isn't installed ([source](https://github.com/data-privacy-stack/presidio/blob/2.2.366/presidio-analyzer/presidio_analyzer/nlp_engine/spacy_nlp_engine.py)). So a pipeline without network access fails on its first line, and one with access installs a model of about 400 MB as a side effect ([en_core_web_lg 3.8.0](https://github.com/explosion/spacy-models/releases/tag/en_core_web_lg-3.8.0)).

`lib.pii.detector` configures the engine itself, with `NoOpNlpEngine`, which loads no language model ([source](https://github.com/data-privacy-stack/presidio/blob/2.2.366/presidio-analyzer/presidio_analyzer/nlp_engine/no_op_nlp_engine.py)). What that costs is context. With a model, Presidio raises a pattern's score when a word such as "phone" appears near the match, by comparing the lemma of each nearby word with each recognizer's context terms ([Presidio's tutorial on context](https://github.com/data-privacy-stack/presidio/blob/2.2.366/docs/tutorial/06_context.md)). With no model there are no lemmas, so the engine can't use the text's context words at all. The engine has one more way onto the network. Its [email recognizer](https://github.com/data-privacy-stack/presidio/blob/2.2.366/presidio-analyzer/presidio_analyzer/predefined_recognizers/generic/email_recognizer.py) checks domains with tldextract, which fetches the Public Suffix List the first time it's used ([tldextract {{version:tldextract}}'s README](https://github.com/john-kurkowski/tldextract/blob/5.4.0/README.md)). Importing Presidio imports tldextract, whose README says an empty `TLDEXTRACT_PUBLIC_SUFFIX_LIST_URLS` turns the fetch off if it's set before the import. So `lib/__init__.py`, which Python runs before any module of the book's `lib`, empties the variable. If an example imported Presidio first, the same file replaces tldextract's [shared extractor](https://github.com/john-kurkowski/tldextract/blob/5.4.0/tldextract/tldextract.py) with one that has no URLs. `lib.pii` refuses to load if any remain, and tldextract uses the copy of the list it ships with, so the same text gives the same answer on every machine.

The defaults are tested on real text: load every predefined recognizer on one of the platform's support tickets, which holds a name, an email, a phone number and a date:

[Example: presidio-offline-engine](../examples/presidio-offline-engine.py)

Presidio's defaults on this engine see the email and the phone number, and miss the colleague's name. `en_core_web_lg` isn't installed, so a bare `AnalyzerEngine()` would try to download it, and tldextract has {{out:presidio-offline-engine:URLs tldextract would fetch the Public Suffix List from}} URLs to fetch its list from. The no-model engine loads {{out:presidio-offline-engine:recognizers loaded}} recognizers, and none of them looks for names, so Jennifer Abbott, the colleague in the ticket, goes unnoticed. Her email is found with a score of {{out:presidio-offline-engine:EMAIL_ADDRESS on jennifer.abbott@example.net}}, and its domain is found again as a URL, at {{out:presidio-offline-engine:URL on example.net}}. The learner's phone number, an 11-digit number typed without separators, is found three times: as a phone number at {{out:presidio-offline-engine:PHONE_NUMBER on •••••••0440}}, a US bank number at {{out:presidio-offline-engine:US_BANK_NUMBER on •••••••0440}} and a US driver's licence at {{out:presidio-offline-engine:US_DRIVER_LICENSE on •••••••0440}}. Even the phone number is found by chance. The learner's country is {{out:presidio-offline-engine:the learner's country}}, but of Presidio's default regions, the US among them, the digits are valid only in {{out:presidio-offline-engine:default regions where it's valid}}. The date of the problem, `12/03`, is read as a date too, which says nothing about anyone.

Those scores aren't probabilities. Each pattern carries a constant score, and weak patterns get low ones, as Presidio's tutorial explains for a five-digit zip code ([Presidio docs](https://github.com/data-privacy-stack/presidio/blob/2.2.366/docs/tutorial/06_context.md)). A US bank number is any run of 8 to 17 digits ([supported entities](https://github.com/data-privacy-stack/presidio/blob/2.2.366/docs/supported_entities.md)), and the FAQ admits that a driver's licence "could be any 9-digit number" ([FAQ](https://github.com/data-privacy-stack/presidio/blob/2.2.366/docs/faq.md)). The analyzer's default threshold is {{out:presidio-offline-engine:default score threshold}}, so every weak match comes back.

**Working rule:** Configure Presidio's engine explicitly: `NoOpNlpEngine` when you run patterns only, or a pinned model you install yourself when you need its names. Never call `AnalyzerEngine()` bare in a pipeline, and pin anything a recognizer would download, such as the Public Suffix List. Read each score as a constant set for its pattern, never as a probability.

## Sample a column's values the same way every run {#sample-column-values}

Scanning every value of every text column is too slow for any warehouse, so tools sample. OpenMetadata's workflow samples rows and checks them with an entity recognition engine ([OpenMetadata docs](https://docs.open-metadata.org/v2.0.x/how-to-guides/data-governance/classification/auto-classification/auto-pii-tagging)). A sample needs three decisions. **Which rows:** a random sample, not the first rows or a block from a random start. Google's Sensitive Data Protection offers a random-start mode, `RANDOM_START`, which begins at a random row and reads on ([Google Cloud docs](https://cloud.google.com/sensitive-data-protection/docs/inspecting-storage)). On a table ordered by sign-up date, that block is one cohort of learners. **The same rows every run**, so a classification can be reproduced and a change in it means the data changed. And **how many**, from how rare the data you must catch is.

DuckDB's reservoir sample takes a seed, but a seed gives a reproducible sample only when DuckDB runs on one thread, as the [DuckDB {{version:duckdb}} docs](https://duckdb.org/docs/2.0/sql/samples) warn. `lib.pii.sample` sets one thread, filters out NULLs and then draws a seeded reservoir sample.

A rare value needs a bigger sample, and the arithmetic says how much bigger. Call the share of values that hold personal data p. The chance that n sampled values include at least one is

chance = 1 − (1 − p)ⁿ

and the n that gives a 99% chance is ln(0.01) / ln(1 − p). This is a rule of thumb: it treats the draws as independent, which a sample without replacement from thousands of rows nearly is.

Put the formula to work: draw 20 notes from `crm.learners` twice, then compare the chances over every row with those over the notes alone.

[Example: seeded-column-sample](../examples/seeded-column-sample.py)

The draws repeat, so a sample can be audited. With the same seed, the second draw returns the same 20 notes, and the third note already holds a phone number, which the output masks.

Of the {{out:seeded-column-sample:learners}} learners, {{out:seeded-column-sample:learners with notes}} have notes, and {{out:seeded-column-sample:notes holding personal data the detector finds}} of those hold personal data that the platform's detector, [tuned later in this chapter](#tune-the-recognizers), finds. The NULLs dilute the sample, since a NULL can't hold personal data. Twenty sampled rows catch personal data {{out:seeded-column-sample:chance 20 sampled rows catch one}} of the time, and a 99% chance takes {{out:seeded-column-sample:sampled rows needed for a 99% chance}} rows. Counted over the notes that exist, twenty catch it {{out:seeded-column-sample:chance 20 sampled notes catch one}} of the time, and {{out:seeded-column-sample:sampled notes needed for a 99% chance}} are enough for 99%.

**Working rule:** Sample non-null values, with a fixed seed, on one thread, and keep the seed with the result. Size the sample from the rarest personal data you must catch, with n = ln(0.01) / ln(1 − p) for 99%. The platform samples {{out:seeded-column-sample:values the platform samples per text column}} values per text column, set in `governance/pii.toml`, which catches personal data held by {{out:seeded-column-sample:rarest share that sample catches 99% of the time}} values or more 99% of the time. For anything rarer, scan the whole column, or classify it by rule.

## Classify columns from their values {#classify-columns-from-their-values}

[The name rules](#classify-columns-from-the-schema) and [a reproducible sample](#sample-column-values) combine into one proposal per column. `lib.pii.classify` takes the strictest classification that either supports: the entity the name suggests, and every entity found in any sampled value. A column with no evidence gets `internal`, because a detector that found nothing has shown nothing, and only a person decides that a column is `public`.

Strictest is a choice. Presidio's own tool for tables, Presidio structured, gives each column one entity, and its default, Most Common, picks the entity that occurs most often ([Presidio docs](https://github.com/data-privacy-stack/presidio/blob/2.2.366/docs/structured/index.md)). That suits choosing how to mask a column. For classifying it, a column that holds one card number in 200 values still holds card numbers.

Proposals for every column of the catalog, from the platform's detector, whose recognizers [a later section](#tune-the-recognizers) chooses, show where each differs from the reviewed metadata:

**Working rule:** Propose the strictest classification that the name or any sampled value supports, with `internal` as the floor, and show the evidence with the proposal. A proposal stricter than the reviewed metadata is a finding for the table's owner, who raises the classification or records why not; never let a detector lower one. OpenMetadata skips any column that already carries a PII tag; we recommend sampling every text column on every run instead, because the reviewed tag is the thing being checked.

## Measure a detector against labelled spans {#measure-against-labelled-spans}

A column-level answer is enough to classify `support.tickets.body`, but not to mask it: masking replaces each span of personal data in each text, and a span the detector misses stays readable. To know what a detector misses, compare its spans with [the truth](#finding-personal-data), the labelled spans of every ticket and review. Two matching rules are standard, and `lib.pii` applies both.

**Exact** matching, from the CoNLL-2003 shared task, counts an entity "correct only if it is an exact match of the corresponding entity in the data file" ([Tjong Kim Sang and De Meulder, 2003](https://aclanthology.org/W03-0419.pdf)). **Overlap** matching asks only for one shared character, with a label of its type, which the SemEval-2013 task on drug interactions calls "Type matching" ([Segura-Bedmar et al., 2013](https://aclanthology.org/S13-2056.pdf)). Neither credits a span hidden under another label, so `lib.pii` adds a third measure, **coverage**: whether every character of the span is inside some detection, whatever its label. Exact asks whether the detector labelled the whole span right, overlap whether it noticed the span as what it is, and coverage whether masking its detections hides the span.

`lib.pii.score` computes exact and overlap matching as **recall**, the share of labelled spans of each type that a detector finds with a label of that type, and **precision**, the share of each label's detections that match a labelled span. `lib.pii.coverage` gives the share of each type's spans covered. `score` also counts the texts in which every labelled character falls inside some detection, the texts that masking would leave with nothing personal. The Text Anonymization Benchmark protects a person only when all of their mentions are masked ([Pilán et al., 2022](https://aclanthology.org/2022.cl-4.19.pdf)), and the platform counts whole texts, which is stricter. Recall comes first: Presidio's evaluation guide says it often matters more than precision, because missing personal data is the error to avoid ([Presidio docs](https://github.com/data-privacy-stack/presidio/blob/2.2.366/docs/evaluation/index.md)).

The defaults find every email, IBAN and date of birth, most phone and card numbers, and no names or street addresses at all, which is most of what the tickets hold. Most of what they flag is wrong: {{out:measure-pattern-recognizers:precision of all detections, exact}} of all detections match a labelled span. The {{out:measure-pattern-recognizers:US_BANK_NUMBER, detections}} US bank numbers, {{out:measure-pattern-recognizers:US_DRIVER_LICENSE, detections}} driver's licences and {{out:measure-pattern-recognizers:URL, detections}} URLs are all wrong. Phone, card and invoice numbers, all runs of digits, come out as bank numbers and licences, and pieces of emails and a few addresses come out as URLs. A wrong label still hides the digits, so phone and card numbers are covered more often than they're found.

Masking would leave personal data in most texts that hold it. Only {{out:measure-pattern-recognizers:texts with every labelled span masked}} of the {{out:measure-pattern-recognizers:texts holding personal data}} texts would come out with nothing personal left.

The truth has its own limits, because the text is generated. Every ticket and review is built from {{out:measure-pattern-recognizers:sentence templates the texts are built from}} sentence templates in `prep/generate.py`, so each [hard case](#where-patterns-fail) is one sentence frame, and all {{out:measure-pattern-recognizers:dates of birth written like 1985-03-12}} dates of birth are written like `1985-03-12`. The date recall of {{out:measure-pattern-recognizers:DATE_TIME, recall, exact}} therefore measures one format: in the generator's own sentence, Presidio finds {{out:measure-pattern-recognizers:dates found in a date of birth written 1985-03-12}} date when the date of birth is written `1985-03-12`, and {{out:measure-pattern-recognizers:dates found in a date of birth written 12 March 1985}} when it's written `12 March 1985`. A measure on this text tells you how a detector behaves on these shapes, not how it will do on yours.

**Working rule:** Measure every detector against labelled spans before it masks anything: recall per entity type by exact and by overlap matching, both with a label of the right type, coverage whatever the label, precision per label, and the share of texts with nothing personal left. Weigh recall first. Before you trust a detector on your text, label a few hundred real records by hand and measure on those too.

## Tune the recognizers against the truth {#tune-the-recognizers}

[Presidio's defaults](#measure-against-labelled-spans) return every weak match. The FAQ names two remedies, changing the acceptance threshold and removing the recognizers a dataset doesn't need, and it notes a trade-off between false positives and false negatives ([FAQ](https://github.com/data-privacy-stack/presidio/blob/2.2.366/docs/faq.md)). Presidio 2.2.364 added per-recognizer and per-entity score thresholds, with the analyzer's default as the fallback ([changelog](https://github.com/data-privacy-stack/presidio/blob/2.2.366/CHANGELOG.md), [release notes](https://github.com/data-privacy-stack/presidio/releases/tag/2.2.364)). The phone recognizer has one more setting that matters on a platform whose learners live in many countries: the regions whose numbering plans it reads ([source](https://github.com/data-privacy-stack/presidio/blob/2.2.366/presidio-analyzer/presidio_analyzer/predefined_recognizers/generic/phone_recognizer.py)).

`governance/pii.toml` keeps {{out:tune-pattern-recognizers:recognizers kept}} recognizers, for the identifiers the platform's text can hold, each with its own threshold. The phone regions aren't a setting: `lib.pii.countries` reads the countries the learners live in from `crm.learners`, so the regions follow the data. Four settings are scored against the same truth:

[Example: tune-pattern-recognizers](../examples/tune-pattern-recognizers.py)

The obvious fix fails. One threshold of 0.5 removes the weak matches and every phone number with them, because a phone number scores {{out:presidio-offline-engine:PHONE_NUMBER on •••••••0440}} when no context word can raise it. Keeping only the {{out:tune-pattern-recognizers:recognizers kept}} recognizers, each with its own threshold, and setting the phone threshold at the score a phone number gets, raises precision to {{out:tune-pattern-recognizers:kept recognizers, own thresholds, precision, exact}} and leaves phone recall where it was. Reading phone numbers in the learners' regions, rather than Presidio's default regions, raises phone recall to {{out:tune-pattern-recognizers:kept recognizers, learners' phone regions, phone recall, exact}}.

One number goes the wrong way: fewer texts come out fully masked than with the defaults. The dropped recognizers had masked some phone and card numbers under the wrong label, which still hides the digits. Without them, coverage falls from {{out:tune-pattern-recognizers:Presidio's defaults, phones covered, any label}} to {{out:tune-pattern-recognizers:kept recognizers, own thresholds, phones covered, any label}} for phone numbers, and from {{out:tune-pattern-recognizers:Presidio's defaults, cards covered, any label}} to {{out:tune-pattern-recognizers:kept recognizers, own thresholds, cards covered, any label}} for card numbers. We think precision is worth the price, because detections are the evidence a reviewer reads, and with the defaults the tickets and reviews hold {{out:measure-pattern-recognizers:US_BANK_NUMBER, detections}} bank numbers and {{out:measure-pattern-recognizers:US_DRIVER_LICENSE, detections}} driver's licences, none of them real. `governance/pii.toml` maps neither entity to a classification, so they change no proposal, but each is a finding someone has to read and dismiss. Dropping the US recognizers is also a claim about the platform's text: the truth holds no US bank or licence numbers. If the platform ever asks for one, that claim, and the measurement, must change.

**Working rule:** Never run with Presidio's default threshold of 0, or with one threshold for every recognizer. Keep only the recognizers for identifiers your text can hold, set each one's threshold from its own scores, and read phone numbers in the regions your users live in, derived from your data. Put all of it in code, and measure again whenever it changes.

## See where patterns fail {#where-patterns-fail}

[The tuned recognizers](#tune-the-recognizers) score well on totals, and totals hide where they fail. A pattern detector fails in three ways: there's no pattern for the thing at all, its pattern or its validation rejects the value, or it matches something that only looks personal. The platform's tickets plant cases of each kind, as its data card says: names typed in lowercase, initials, first names that are ordinary words, phone numbers typed without separators, and invoice numbers, order numbers and dates of a problem, which [the truth](#finding-personal-data) leaves unlabelled. The card pattern's shape causes the card misses. Validation causes the other misses. The IBAN recognizer checks each country's format, length and check digits ([source](https://github.com/data-privacy-stack/presidio/blob/2.2.366/presidio-analyzer/presidio_analyzer/predefined_recognizers/generic/iban_recognizer.py)). Of the {{out:pattern-hard-cases:phone numbers missed}} phone numbers the detector misses, {{out:pattern-hard-cases:of them, invalid in the learner's country}} aren't valid in the country the ticket's learner lives in, so most of the phone misses are the generator's, not the detector's.

**Working rule:** Read a detector's misses by case, not by total, and keep a list of the cases your text holds. Use patterns for what has a checkable shape, such as emails, IBANs, card numbers, phone numbers and dates, and never for names or addresses. Keep the checksums and numbering plans, because they're what makes the patterns precise. Check the card pattern against the card numbers your payment provider issues, and the date patterns against the ways your users write dates.

## Compare a PII model {#compare-a-named-entity-model}

[The patterns](#where-patterns-fail) have nothing for names or addresses, and those are most of the personal data in the platform's text: {{out:measure-pattern-recognizers:PERSON, labelled}} names and {{out:measure-pattern-recognizers:LOCATION, labelled}} addresses among the {{out:measure-pattern-recognizers:labelled spans}} labelled spans. Finding them takes a model that reads context, not a general named-entity model. The authors of the SPY dataset define PII as the entities that can identify, contact or locate a specific individual, and found that dedicated named-entity models have limits in PII contexts ([Savkin et al., 2025](https://aclanthology.org/2025.naacl-srw.23.pdf)). We use a PII model, one trained for personally identifiable information: OpenAI's Privacy Filter, an Apache-2.0 model with eight fixed labels, such as `private_person`, `private_address` and `account_number` ([model card](https://huggingface.co/openai/privacy-filter/blob/7ffa9a043d54d1be65afb281eddf0ffbe629385b/README.md)).

The labels are the model's own. OpenAI's card says its label policies can't be set while the model runs ([OpenAI, 2026](https://cdn.openai.com/pdf/c66281ed-b638-456a-8ce1-97e9f5264a90/OpenAI-Privacy-Filter-Model-Card.pdf), section 4.2). We chose it over GLiNER2-PII, the runner-up among open PII models, for those fixed labels. GLiNER2-PII takes the labels to look for at inference time, along with a threshold ([model card](https://huggingface.co/fastino/gliner2-privacy-filter-PII-multi/blob/1cb4166094dc58fa8d836429f060d6c95f62b495/README.md)), so a recording of it would have to pin both. Privacy Filter has 1.5 billion parameters, 50 million of them active, and runs on a CPU.

The book's examples never run a model, so they read a recording of its output. The recording, `data/recorded/pii-entities/`, which this chapter and [chapter 9](#replace-personal-data) use, holds every span the model found in every ticket and review, with its offsets, its text and the model's label. `recordings/pii_entities.py` made it on a CPU with the model's reference decoder, `opf` ([code](https://github.com/openai/privacy-filter/tree/f7f00ca7fb869683eb732c010299d901457f19c3)), which chooses the best sequence of labels for a whole text, so most spans come back in one piece rather than token by token. It used the default operating point, with all six transition biases at 0 ([calibration file](https://huggingface.co/openai/privacy-filter/blob/7ffa9a043d54d1be65afb281eddf0ffbe629385b/original/viterbi_calibration.json)); the model can also be set "for improved recall" (section 2.3.2). The manifest pins the model's revision and the SHA-256 of its weights, so anyone can record it again and compare, and `lib.pii.recorded` refuses spans that don't match the text at their offsets. The recording keeps the model's labels, and the example maps them to the truth's types, so a different mapping never needs a new recording. Score the model, the platform's patterns and both together, masking whatever either finds:

Most often it misses the words {{out:privacy-filter-hard-cases:first names that are words, missed most often}} and the instructors' names {{out:privacy-filter-hard-cases:instructors named in reviews, missed most often}}. How much the misses matter depends on their length. The card recommends testing the model in your own domain against local policy references before production use (section 4.5). Record the model's output with its revision, weights and operating point pinned, keep its own labels, and map them in code. Measure it on your own text, by hard case, before use and after every model change; if it misses too much, try an operating point that leans toward recall and record again. Treat masked text as reduced, never as anonymous.

## Count what a wrong label costs {#what-a-wrong-label-costs}

[The comparison with the patterns](#compare-a-named-entity-model) scored the model by exact and overlap matching, which both need a label of the span's type. Masking doesn't read the label: a card number the model labels `private_phone` is still hidden. Classification does, because `governance/pii.toml` maps each entity type to a classification: a phone number to `personal`, a card number to `sensitive`. ## Classify again when the schema changes {#reclassify-on-schema-change}

A classification describes a column at one moment, and [chapter 2](#catch-schema-changes) showed how schemas move under it. So the question is when to classify again, not on every schema ID: in PyIceberg, editing a column's description gives the schema a new ID with no new column. What needs classifying is a [field ID](#key-column-metadata-by-field-id), the number Iceberg gives each column, that the metadata has never seen. Iceberg gives every added column a new one, and a renamed column keeps its ID and so its reviewed classification. Values can also change without a schema change, so the samples of text columns need a rerun on a schedule too. Vendors promise this as a service: Databricks says its classification scans incrementally and classifies new data with no manual setup ([Databricks docs](https://docs.databricks.com/aws/en/data-governance/unity-catalog/data-classification)), a claim we don't test.

The support team wants a number to call learners back on for tickets opened by phone, so it adds a column called `callback_number` to `support.tickets`. The change comes in four steps: edit a description, add the column, fill it from the learners' phone numbers, then classify only the field IDs that `governance/metadata.toml` lacks:

## What goes wrong in production {#personal-data-in-production}

A detector's worst failure is a miss, and its output always looks like a list of findings: what it misses never appears in it:

- **Phone numbers read as bank numbers.** With Presidio's defaults, every run of 8 to 17 digits is a US bank number, and so is every phone number typed without separators. The evidence for the ticket table lists {{out:measure-pattern-recognizers:US_BANK_NUMBER, detections}} bank numbers that aren't there, a report of "bank numbers in tickets" sends someone to the wrong team, and mapping that entity to a classification would raise columns for the wrong reason. Keep only the recognizers your text needs, each with its own threshold, as [the tuning section](#tune-the-recognizers) does, and count detections per label: a label with hundreds of hits and no labelled spans is a false positive.
- **Names in free text missed.** Patterns find no names, and [the model](#read-the-models-misses) misses some lowercase names, first names that are also words, and first names standing alone. Ticket {{out:privacy-filter-hard-cases:first ticket with a lowercase name both detectors miss}} still says "this is {{out:privacy-filter-hard-cases:the name, as typed}}, i still can't log in" after both detectors have run, and passes every check that counts detections. You notice only by measuring recall against labelled text, per hard case, and by reading a sample of masked output.
- **Personal data in a column called `notes`.** No name rule marks it, and a reviewer who never read it classifies it `internal`. Sample every text column's values, and treat free-text columns as personal until a sample says otherwise.
- **A column more sensitive than its metadata.** Learners paste card numbers into tickets, so `support.tickets.body` holds `sensitive` data under a `personal` classification. Compare every proposal with the reviewed metadata, and route a stricter one to the table's owner.
- **A detector that reaches the network.** `AnalyzerEngine()` downloads a model, and tldextract fetches the Public Suffix List. Offline, the pipeline fails; online, the same text can be classified differently on two machines. A setting read at import holds only if it's made before anything imports the library. Configure the engine, pin what it would fetch, check that the setting held, and run the detector's tests with the network off.
- **Truth shaped by its generator.** The platform's text comes from {{out:measure-pattern-recognizers:sentence templates the texts are built from}} sentence templates filled by Faker, which writes every date of birth one way, phone numbers that aren't valid where the learner lives, and street names built from people's names. Read the misses before trusting a recall figure, and measure again on labelled samples of your own text.

## What this chapter decided {#personal-data-decisions}

- **Columns are classified from their name, their type and their values.** Name rules run on every column; text columns are sampled; the strictest evidence wins, with `internal` as the floor, and only a person sets `public`.
- **Samples are reproducible:** {{out:seeded-column-sample:values the platform samples per text column}} non-null values per text column, by a seeded reservoir sample on one DuckDB thread.
- **Presidio runs offline,** on `NoOpNlpEngine`, with {{out:tune-pattern-recognizers:recognizers kept}} recognizers, each with its own threshold, phone regions read from the learners' countries, and tldextract's own copy of the Public Suffix List, checked when `lib.pii` loads.
- **Detectors are measured against labelled spans:** recall per entity type by exact and overlap matching with a label of the right type, coverage whatever the label, precision per label and texts left with nothing personal, with recall weighed first.
- **A proposal stricter than the metadata is a finding:** `support.tickets.body` goes to `team-support` as `sensitive`, and `billing.payments.card_number` to `team-billing`, with the evidence that it holds full card numbers.
- **Free text is masked with two detectors:** OpenAI's Privacy Filter, recorded at a pinned revision and operating point, for names and addresses, and the tuned patterns for card numbers, IBANs and phone numbers, whose checksums keep card numbers labelled as cards. Masking hides whatever either finds; neither is trusted to make text anonymous.
- **No example prints a whole phone number, card number or IBAN:** `lib.pii.masked` keeps the last four digits.
- **Reclassification follows field IDs:** every field the metadata lacks is classified in the pull request that adds it, and text columns are sampled again on a schedule. A detector is only as good as the measurement behind it, and what it misses never appears in its output. The measurement is what tells a team which of its classifications it can rely on, and which it has to check by hand.
